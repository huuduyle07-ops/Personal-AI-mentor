## 1. 프로젝트 개요

Personal Accountability AI는 일일 진행 상황을 확인하고, 사용자가 보고한 성과를 검증하며, 행동 변화를 파악하고, 사용자의 상황에 맞게 상호작용을 조정하는 능동적인 도우미를 목표로 합니다.

시스템은 다음 요소를 결합하고자 합니다.

- **목표 실천 지원(Accountability):** 사용자의 약속과 일일 목표를 추적합니다.
- **적응(Adaptation):** 사용자의 행동과 상황에 따라 상호작용을 조정합니다.
- **검증(Verification):** 작업 완료 여부와 학습 결과를 평가합니다.
- **영속적 메모리(Persistent Memory):** 과거 맥락, 진행 상황, 지식 상태를 유지합니다.
- **효율적인 추론(Efficient Intelligence):** 불필요한 대규모 언어 모델(LLM) 추론을 줄입니다.
- **지속적인 실험(Continuous Experimentation):** 측정 가능한 실험으로 시스템 설계를 개선합니다.

초기 구현은 상업적 배포나 제삼자 모니터링이 아닌 개인 실험을 위한 것입니다.

### 핵심 철학

> 관찰 → 이해 → 결정 → 검증 → 적응 → 평가

실험 하나가 실패했다고 해서 프로젝트 전체가 실패한 것은 아닙니다. 모든 실험은 근거를 제공하거나, 한계를 드러내거나, 유용한 연구 질문을 만들어야 합니다.

## 2. 프로젝트 목표

적응형 도우미가 다음을 수행할 수 있는지 연구합니다.

1. 능동적으로 일일 진행 보고를 요청합니다.
2. 목표 달성과 평소와 다른 행동 양상을 구분합니다.
3. 사용자가 정직하지 않다고 단정하지 않고 자기 보고 정보를 평가합니다.
4. 지식 유지와 기억에 문제가 있을 가능성을 파악합니다.
5. 수면 부족, 늦은 근무, 예상치 못한 의무 등의 상황에 맞게 일정을 조정합니다.
6. 적응형 의사결정 라우팅으로 추론 비용을 줄입니다.
7. 복잡하거나 모호한 상황을 적절한 LLM에 전달합니다.
8. 사용자의 자율성을 해치지 않으면서 이전 상호작용에서 학습합니다.

**핵심 요구사항:** 안전 규칙, 권한 검사, 실행 제약은 학습된 의사결정 정책과 독립적으로 작동해야 합니다.

### 3.1 이벤트 우선순위 체계

운영체제의 스케줄링 개념을 참고하여 세 가지 논리적 우선순위를 사용합니다.

| 우선순위 | 분류 | 예시 |
|---|---|---|
| P1 | GENERAL | 일일 보고, 일반적인 질문 |
| P2 | SYSTEM | 검증, 재시도, 예약된 리뷰 |
| P3 | URGENT | 즉각적인 대응이 필요한 이벤트 |

이벤트 우선순위와 LLM 라우팅 결정은 별개의 문제입니다.

URGENT 이벤트는 추론 서비스를 사용할 수 없을 때도 규칙 기반 대체 동작을 제공해야 합니다.

스케줄러는 낮은 우선순위 이벤트가 무기한 밀리지 않도록 공정성을 보장해야 합니다.

이 우선순위 체계는 애플리케이션 수준에서 작동하며 FreeRTOS를 필요로 하지 않습니다.

## 4. 적응형 의사결정 모델

### 4.1 Mamba를 검토하는 이유

Mamba는 시퀀스 모델링을 위해 설계된 선택적 상태 공간 아키텍처입니다.

이 프로젝트는 작은 Mamba 기반 네트워크가 **순차 의사결정 정책(sequential decision policy)**으로 기능할 수 있는지 연구합니다.

모델이 학습하고자 하는 관계는 다음과 같습니다.

- 사용자의 과거 행동.
- 현재 이벤트와 보고된 활동.
- 작업 완료 패턴.
- 메시지의 특성.
- 도우미가 이전에 수행한 동작.
- 이전 결정의 결과.

모델의 출력은 실행 명령이 아닌 동작 제안입니다.

### 4.2 의사결정 행동 공간

초기 행동 공간은 다음과 같습니다.

```python
ACTIONS = [
    "RULE_RESPONSE",
    "ASK_FOLLOWUP",
    "LOCAL_LLM",
    "DEFER",
    "REQUEST_REVIEW"
]
```

클라우드 추론은 별도의 권한 및 안전 정책으로 통제합니다.

의사결정 모델은 독자적으로 명령을 실행하거나, 행동 공간을 수정하거나, 시스템 제약을 우회해서는 안 됩니다.

### 4.3 입력 표현

초기 실험에서는 원시 자연어 토큰 대신 구조화된 행동 특성을 사용합니다.

후보 특성은 다음과 같습니다.

```text
message_length
message_type
task_completion_ratio
sleep_duration
energy_level
response_delay
recent_completion_trend
previous_followup_count
verification_status
time_since_last_checkin
```

누락된 값은 명시적으로 표현해야 합니다.

사용자가 직접 보고한 관찰, 모델이 생성한 추론, 검증된 정보는 서로 구별할 수 있어야 합니다.

### 4.4 행동 기준선

비교 가능한 활동의 이력을 바탕으로 기준선을 유지합니다.

예를 들어 일일 학습 목표가 30분인 경우 다음과 같이 해석합니다.

| 보고된 시간 | 해석 |
|---|---|
| 5분 | 목표 미달 |
| 30분 | 목표 달성 |
| 90분 | 목표 달성 및 평소보다 높은 긍정적 편차 |

이례적으로 높은 결과가 나왔다고 해서 향후 목표를 자동으로 높여서는 안 됩니다.

평소와 다른 행동은 해석이 필요한 관찰이며, 기만의 증거가 아닙니다.

콜드 스타트 기간에는 과거 데이터가 부족하므로 확신에 찬 판단 대신 기준선의 불확실성을 나타내야 합니다.

## 5. 모델 학습 전략

### A단계 — 지도학습 기준 모델

행동 이벤트 시퀀스와 라벨이 부여된 라우팅 결정을 포함하는 데이터셋을 만듭니다.

비교 대상은 다음과 같습니다.

- 규칙 기반 라우팅.
- 로지스틱 회귀.
- 의사결정 트리.
- 소형 MLP.
- GRU.
- Tiny Mamba.

합성 데이터는 엔지니어링 테스트와 알고리즘 개발에 사용할 수 있습니다. 다만 합성 데이터 평가 결과를 실제 사용자에게 효과가 있다는 근거로 제시해서는 안 됩니다.

### B단계 — 온폴리시 지식 증류(On-Policy Distillation)

더 강력한 교사 정책(teacher policy)의 지도를 이용해 Mamba 학생 정책(student policy)을 학습하는 방법을 연구합니다.

제안하는 학습 흐름은 다음과 같습니다.

1. 학생이 시뮬레이션된 상태를 관찰합니다.
2. 학생이 동작을 선택합니다.
3. 환경이 다음 상태를 생성합니다.
4. 교사는 학생이 실제로 마주친 상태를 평가하고 목표 행동 분포를 제공합니다.
5. 학생은 적절한 증류 목적함수로 정책을 갱신합니다.
6. 이를 반복한 뒤 학습에 사용하지 않은 데이터로 평가합니다.

후보 목적함수는 다음과 같습니다.

\[
\mathcal{L}_{OPD}
=
\mathbb{E}_{s\sim d^{\pi_\theta}}
\left[
D_{KL}
\left(
\pi_T(\cdot \mid s)
\parallel
\pi_\theta(\cdot \mid s)
\right)
\right]
\]

각 기호의 의미는 다음과 같습니다.

- \(\pi_\theta\): 학생 정책.
- \(\pi_T\): 교사 정책.
- \(d^{\pi_\theta}\): 학생 정책으로 수행한 롤아웃에서 만들어지는 상태 분포.

온폴리시 학습을 위해서는 학생의 현재 정책으로 행동할 때 실제로 마주치는 상태를 수집해야 합니다.

교사가 이산적인 동작 라벨만 제공한다면, 실험은 분포 기반 정책 증류가 아니라 온폴리시 모방학습(on-policy imitation learning)으로 설명해야 합니다.

교사의 판단을 자동으로 정답으로 취급해서는 안 됩니다.

### C단계 — 선택적 크리틱 평가

독립적인 크리틱(critic)이 의사결정 품질을 개선하는지 연구합니다.

제안하는 역할은 다음과 같습니다.

- **Mamba 액터(Actor):** 동작을 제안합니다.
- **MLP 또는 LSTM 크리틱:** 동작의 품질을 추정합니다.
- **규칙 기반 검증기(Deterministic Validator):** 시스템 제약을 적용합니다.

행동 가치 함수의 예시는 다음과 같습니다.

\[
Q_\phi(s_t,a_t)
\]

크리틱은 의미 있는 피드백, 관찰된 결과, 검증된 목표값을 이용해 학습해야 합니다.

다음 세 가지 구성을 평가합니다.

| 실험 | 아키텍처 |
|---|---|
| A | Mamba + Rule Validator |
| B | Mamba + MLP Critic |
| C | Mamba + LSTM Critic |

LSTM 크리틱은 실험적 구성 요소이며 필수 의존성이 아닙니다.

추가되는 복잡성과 계산 비용을 정당화할 만큼 측정 가능한 개선이 있을 때만 유지해야 합니다.

## 6. 일일 목표 실천 흐름

### 6.1 정오 체크인

기본 시간은 **정오 12:00**이며 사용자가 변경할 수 있습니다.

도우미는 진행 보고를 요청하며 다음 활동을 수행할 수 있습니다.

- 일일 작업 완료 상태 갱신.
- 보고된 성과 검증.
- 장애 요인 파악.
- 이전에 학습한 내용 복습.
- 남은 하루에 대한 조정 제안.

### 6.2 저녁 리뷰

도우미는 다음 내용을 요약합니다.

- 완료한 목표.
- 미완료 목표.
- 파악한 장애 요인.
- 추가 복습이 필요한 지식.
- 다음 날 적용할 수 있는 조정.

알림 피로와 불필요한 추론 호출을 줄이기 위해, 관련된 리뷰 활동은 가능하면 같은 상호작용으로 묶어야 합니다.

### 6.3 회복 모드(Recovery Mode)

사용자가 다음 상황을 보고하면 일정 조정을 검토할 수 있습니다.

- 수면 부족.
- 늦은 근무.
- 질병.
- 예상치 못한 의무.
- 평소보다 현저히 낮은 활력.

가능한 조정에는 작업량 축소, 체크인 연기, 추가 휴식, 더 작은 대체 목표 등이 포함됩니다.

사용자가 자고 있는지 확인하려는 목적으로 사용자를 깨워서는 안 됩니다.

## 7. 진행 검증과 학습 메모리

시스템은 사용자가 보고한 활동과 검증된 학습 결과를 구분합니다.

초안에서 제안한 초기 검증 상태는 다음과 같습니다.

| 상태 | 의미 |
|---|---|
| `reported` | 사용자가 보고한 활동 |
| `verified` | 검증 과제를 성공적으로 완료함 |
| `passed_after_support` | 추가 설명을 받은 뒤 통과함 |
| `review_required` | 추가 연습이 필요함 |
| `unknown` | 근거가 충분하지 않음 |

검증 이력은 보존해야 합니다.

이전에 검증된 지식도 이후 관찰에서 잊어버린 것으로 보이면 `review_required`로 돌아갈 수 있습니다.

향후 교육용 하니스(teaching harness)는 관련 공유 메모리에 접근하고 구조화된 학습 결과를 반환할 수 있습니다.

전문 모듈은 관련 없는 사용자 정보를 덮어써서는 안 됩니다.

## 8. 지연 LLM 평가

로컬 LLM을 사용할 수 없거나 즉각적인 추론이 필요하지 않은 이벤트라면, 나중 세션에서 평가하도록 대기열에 넣는 방식을 검토합니다.

예시는 다음과 같습니다.

```json
{
  "event_type": "behavior_review",
  "priority": "SYSTEM",
  "status": "pending",
  "retry_slot": "evening",
  "attempts": 0
}
```

지연 작업에는 다음이 필요합니다.

- 제한된 재시도 횟수.
- 중복 방지.
- 만료 정책.
- 실패 기록.
- 맥락 보존.
- 이벤트가 더 이상 유효하지 않을 때 취소.

안전상 중요한 응답이 지연 추론에만 의존해서는 안 됩니다.

## 9. iOS 단축어 연동

선택적인 단축어 자동화로 앱 실행 또는 종료 이벤트를 보고할 수 있습니다.

초기 예시에는 TikTok, YouTube 등 사용자가 선택한 앱이 포함됩니다.

시스템은 다음 요구사항을 충족해야 합니다.

- 사용자의 명시적 설정과 허가를 요구합니다.
- 필요한 정보만 수집합니다.
- 들어오는 이벤트를 인증합니다.
- 모니터링을 일시 중지하거나 비활성화할 수 있게 합니다.
- 앱 활동을 의도적인 메시지 회피의 증거로 취급하지 않습니다.

이 이벤트들은 불완전한 행동 신호이며, 기기 사용 전체를 기록한 자료가 아닙니다.

## 10. 안전, 개인정보 보호, 권한 관리

### 10.1 안전 관련 대응

의미가 모호한 피로나 괴로움의 표현을 자동으로 긴급 상황으로 분류해서는 안 됩니다.

도우미는 상황 확인, 적절한 즉각 대응, 필요한 경우 사람의 도움으로 연결하는 절차를 지원해야 합니다.

클라우드 LLM을 사용하려면 사용자가 충분한 설명을 듣고 사전에 동의해야 하며, 요청과 관련된 맥락만 전송해야 합니다.

LLM이 독립적으로 사용자의 안전을 보장할 수 있는 것처럼 표현해서는 안 됩니다.

### 10.2 설정 보안

LLM이 만든 설정 제안은 다음 검사를 통과해야 합니다.

1. 엄격한 스키마 검증.
2. 허용 목록에 있는 설정 필드만 수용.
3. 자료형 검증.
4. 허용 값 범위 검증.
5. 변경 한도와 재변경 대기 시간 적용.
6. 권한 검사.
7. 감사 기록과 롤백 지원.

민감한 설정 변경에는 사람의 명시적인 승인이 필요합니다.

유효한 JSON만으로 프롬프트 인젝션을 충분히 방어할 수는 없습니다.

모든 사용자 메시지와 모델 생성 출력은 신뢰할 수 없는 입력으로 다뤄야 합니다.

Python 프로토타입과 인터페이스를 검증한 뒤 다음 구성을 검토합니다.
